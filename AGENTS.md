# AGENTS.md

## Направление проекта

Проект переориентируется на разработку сайта для художника. Основная цель сайта — публично представлять работы автора и дать посетителям простой способ заказать индивидуальную работу напрямую у художника.

## Продуктовая концепция

Сайт должен поддерживать публикацию и презентацию авторских работ, включая:

- картины;
- шаржи;
- рисунки;
- другие визуальные работы автора, если они появятся в дальнейшем.

Посетитель сайта должен иметь возможность:

- просматривать портфолио и отдельные работы;
- получать информацию об авторе и доступных форматах работ;
- отправлять запрос на заказ работы непосредственно автору;
- понимать, какие данные нужны для оформления заказа: описание идеи, формат, сроки, контактные данные и при необходимости референсы.

## Административный блок

В проекте должен быть предусмотрен защищенный административный блок для автора. Он нужен для самостоятельного управления содержимым сайта без участия разработчика.

Минимальные возможности административного блока:

- авторизация и защита от несанкционированного доступа;
- загрузка новых работ;
- редактирование описаний, названий, категорий и метаданных работ;
- скрытие, публикация и удаление работ;
- редактирование основных текстовых блоков сайта;
- управление заявками или заказами, если такая функциональность будет реализована в проекте.

При проектировании административной части важно учитывать безопасность: не хранить секреты в репозитории, валидировать загружаемые файлы, ограничивать доступ к приватным маршрутам и не раскрывать служебные данные клиенту.

## Деплой и сопровождение агентами

Сайт будет деплоиться из этого репозитория на сервер другим агентом. Поэтому при разработке необходимо оставлять проект понятным для автоматизированного сопровождения.

Рекомендации для будущих агентов:

- оставлять комментарии в конфигурационных файлах и нестандартных участках кода, если это поможет безопасному деплою или сопровождению;
- документировать обязательные переменные окружения, команды сборки, миграции и запуска;
- не хардкодить серверные пути, домены, токены, пароли и другие секреты;
- хранить примеры конфигурации в виде `*.example.*` файлов;
- при изменении процесса деплоя обновлять документацию рядом с кодом;
- явно отмечать, какие директории содержат пользовательские загрузки и должны сохраняться между релизами;
- при добавлении фоновых задач, очередей, cron-задач или внешних сервисов описывать их назначение и требования к запуску.

## Общие правила разработки

- Предпочитать ясную структуру проекта и читаемые имена файлов, компонентов и модулей.
- Держать пользовательскую часть сайта, административную часть и серверную/инфраструктурную логику логически разделенными.
- Добавлять комментарии не для очевидного кода, а для решений, которые важны для будущего агента или деплоя.
- Обновлять этот файл, если направление проекта, архитектура или правила сопровождения изменятся.
